ROUND #1

Recommended architecture
Replace Attributes and ConsoleAttributes with small injectable facets:
    Facet	                    Responsibility
    RuntimeConfiguration	    Environment, absolute project paths, resolved XML configuration, and DisplayErrors policy
    LoggerService       	    Wraps the selected Lucinda\Logging\Logger
    HeadersService      	    Wraps Lucinda\Headers\Wrapper
    SqlService / NoSqlService   Wrap the final engine providers
    TranslationService	        Wraps Internationalization\Reader
    SecurityContext	            Current packet, user ID, CSRF token, bearer token, and relevant OAuth2 state

Listeners should receive existing facets through constructor injection and return one new facet where appropriate. Use separate listeners rather than MultiFaceted until the FacetCollection iteration bug is fixed.
A scheduler factory should define lifecycle ordering centrally:
START
  Runtime configuration

APPLICATION
  SQL provider
  NoSQL provider

REQUEST
  STDERR format synchronization
  Logging
  Headers
  CORS/preflight
  Localization
  Security

RESPONSE
  Cache/status/header transformation

END
  Process-wide registry cleanup, if used
ServiceRegistry should be retained only where a dependency constructs project classes without injection—particularly security DAOs and custom PHP session handlers. Normal controllers, listeners, and resolvers should use facets.

Specific additions I consider worthwhile:
Security integration
Engine already has RequestBinder and the OAuth service converters, but the actual fixed orchestration is missing:
1. Bind MVC request to security request.
2. Build OAuth client drivers and convert them through ServiceBinder.
3. Build RolesDetector for XML authorization.
4. Run WebSecurity\Wrapper.
5. Publish a stable SecurityContext facet containing the resulting packet, user ID, CSRF token and access token.
The Security API correctly leaves redirects and responses to its caller—see [Security Wrapper (line 33)](Z:/home/aherne/framework/framework-skeleton/vendor/lucinda/security/src/Wrapper.php:33). Engine should therefore provide packet interpretation primitives, while Skeleton decides whether a failure becomes a redirect, JSON response or rendered page.
A session-backed OAuth2State implementation is also sufficiently generic for Engine. SQL/NoSQL variants can follow later.
Rendering
The old HTML, JSON and console resolvers are integration adapters, not application logic. They should be reusable Engine classes.
The JSON resolver should encode the view data directly. The old "status": "ok/error" envelope and its debug_backtrace() detection are application policy and should not be embedded in Engine.
Headers and caching
A cache response listener can implement both Body and Headers: transform() receives the body, computes the ETag, and getExtraHeaders() returns the validators. That fits the new response API much better than AbstractCacheable(Response $response).
CORS preflight handling is generic too, including termination via a prepared MVC response.
Error integration
Engine should replace AbstractReporter with an implementation of the new ErrorReporter contract. It should accept a logger or logger provider instead of depending on the old STDERR request object.
The default mapping of Lucinda exceptions to error category and recommended HTTP status is also fixed cross-package knowledge. The old Configurer hardcoded this in generated XML. Engine should expose that mapping as a versioned catalog so both the Skeleton and future Configurer can consume it.
Cross-feature validation
The old [FeaturesValidator (line 20)](Z:/home/aherne/framework/framework-skeleton/vendor/lucinda_old/framework-configurer/src/FeaturesValidator.php:20) contains cross-package rules such as migrations requiring storage and security requiring appropriate persistence.
Those rules should not live only in an installer. Engine should provide a framework-level configuration validator/capability graph, used:
- at runtime for fail-fast structural validation;
- by skeleton integration tests;
- later by Configurer before writing anything.
Network connection checks should remain an explicit Configurer diagnostic, not part of ordinary runtime validation.
Useful generic infrastructure, but second priority
After the vertical skeleton works, Engine could also provide:
- Storage-independent throttling policy, leaving state persistence to the DAO.
- Parameterized SQL and NoSQL session handlers.
- SQL/NoSQL migration-state adapters.
- Trusted-proxy/client-IP resolution shared by logging and security.
- Explicit environment-variable/secret resolution for configuration.
- A scoped service locator for legacy no-argument DAOs.
I would not resurrect the old AbstractLoginThrottler exactly. Its exponential-delay calculation is generic, but persistence and time handling should be separated into a pure policy object and a storage adapter.
What should not enter Engine
These belong elsewhere:
- Sample controllers, views, CSS and tags: Skeleton.
- Authentication and authorization DAOs: Skeleton/application.
- Users, roles, routes and seed data: application configuration or migrations.
- Concrete SQL schema: migrations owned by the selected application profile.
- REST response envelopes and error-page appearance: Skeleton policy.
- Virtual-host installation and operating-system service control: Configurer/dev tooling.
- Feature prompts and file generation: Configurer.
Engine should also not become a large static service container.
